# ArtisanPack UI PageSpeedInsights Changelog

## [Unreleased]

### Added

- **Five React components** — `ScoreCard`, `CoreWebVitalsCard`, `OpportunitiesTable`, `TrendChart`, and `UrlManager` — built on `@artisanpack-ui/react` and reading the JSON endpoints. Each renders the same states as the Livewire component of the same name, because a React card and a Livewire card describing the same stored row must not disagree about which piece of news it is: "no field data" stays distinct from "origin-level data", an unscored category renders as an em dash rather than a zero, and an empty opportunities list is still spelled three ways. They ship as TypeScript sources under `resources/js/react` rather than as a build — the components take their styling from the host application's Tailwind and daisyUI theme, so they have to reach its pipeline before it compiles — and publish with `php artisan vendor:publish --tag=pagespeed-insights-js`.
- **A framework-free fetch layer** at `resources/js/shared`: one typed client per endpoint, plus the request plumbing they share, so the React and the forthcoming Vue components talk to one server payload rather than to two hand-written approximations of it. Every refusal arrives as a `PageSpeedInsightsError` carrying the endpoint's stable `error` code alongside its prose message, so a client branches on the code rather than on the wording — which is what stops a front end breaking the moment somebody improves a sentence, or the moment the server runs in a locale the client does not read. The names and theme colours the endpoints deliberately do not send are resolved in `labels.ts`, once, for both frameworks.
- **A finished run announces itself to the rest of the page**, the way the Livewire score card dispatches `pagespeed-insights:result-stored`. The score card is the only component that queues a run, so it is the only one that knows when a new row lands; the vitals card and the opportunities table refresh when the announcement names their URL *and* their form factor, and the trend chart refreshes on either, because it plots both. Without it a page shows fresh scores beside three panels describing the previous run, which reads as a page that has finished updating when it has not. A timed-out ticket announces nothing, because no row appeared and re-reading three panels to show the data they already show is noise. The announcement lives in the shared layer rather than in the React components — so the Vue half gets the same behaviour — and is dispatched on `window` as well as to in-process listeners, so a surface built with neither component set can hear it.
- **The trend line is drawn as inline SVG rather than by the component library's chart.** A trend carries one series per form factor, each on its own timestamps, with nulls where a completed run lost the measurement; `Chart` takes a series as a plain `number[]` against shared labels, which expresses neither — and it pulls in ApexCharts, an optional peer a host application need not have installed. Drawn by hand, a gap in the history stays a gap in the line, which is the whole reason the server sends nulls rather than skipping the point.
- **Authenticated JSON endpoints** behind a configurable prefix and middleware stack (`routes.enabled`, `routes.prefix`, `routes.middleware`), backing the React and Vue components and any front end an application writes for itself: `GET /pagespeed/scores`, `/core-web-vitals`, `/opportunities`, and `/trends`; `GET`, `POST /pagespeed/urls` and `DELETE /pagespeed/urls/{id}`; `POST /pagespeed/test` and `GET /pagespeed/results/{id}`. Replacing `routes.middleware` replaces it wholesale, `auth` entry included — the package applies the stack that is configured rather than adding a guard of its own on top of it — and `routes.enabled` off registers nothing at all, which is the right setting for an installation that only uses the commands, the queue, and the Livewire components. An endpoint nobody calls is still an endpoint somebody can call.
- **Reading and testing are scoped differently, and deliberately not by the same rule.** Authentication is not the whole of the question, because every endpoint takes a URL from the caller. The read endpoints only ever answer for URLs in this installation's own monitored set — the results table is keyed on a plain URL column, so without the check an authenticated user could read whatever this installation happens to have stored about a third party's site, including runs somebody queued from the console while looking at a competitor. `POST /test` and `POST /urls` accept a monitored URL *or* one on the application's own origin, because testing a page of your own site that nobody has added to the list yet is the obvious thing an ad hoc run is for. Both are widened by `routes.allow_external_urls` (`PAGESPEED_ALLOW_EXTERNAL_URLS`, off by default), for the agency case; the read endpoints are never widened by it. A refusal is a `403` with a stable `error` code, and it is the same refusal whether the URL is somebody else's site or simply one this installation has never added, so that the monitored set cannot be mapped by probing it.
- **The endpoints carry no authorization of their own beyond the configured middleware**, which is the same stance the Livewire components take and is stated rather than left to be discovered: an authenticated user is an authorized one, so an installation where "logged in" is broader than "allowed to manage performance monitoring" puts its own policy in `routes.middleware`. Nor is there a `throttle` in the default stack — the job middleware holds the whole application to `rate_limit.per_minute` API requests so the quota itself is safe, but nothing stops an authenticated user filling the queue, and the README says which middleware to add where that matters.
- **Adding a URL is held to the test scope rather than the read scope**, because it is a *recurring* commitment of quota: every cycle, on every configured form factor, for as long as the row lives. An open `POST /urls` is a worse quota vector than an open `POST /test`, not a lesser one.
- **`POST /test` returns a ticket rather than a result id, and the ticket resolves to the row the run produced.** A queued run has no row until it finishes, and the two obvious ways to hand back an id anyway are both worse: writing a pending row would put a third status into a table every other reader of which assumes two, so `latestFor()` would start returning a scoreless row and the score card, the vitals card, and the opportunities table would each render an in-flight run as a completed one that measured nothing; returning the newest existing id and letting the client watch for a bigger one pushes the mechanism into every consumer, one of which will get it subtly wrong and show a stale result as a fresh one. So the watch is kept server-side, and a run finishing is simply a newer row appearing — there is no separate "is it done" channel that could disagree with the database. Past ten minutes the ticket reports `timed-out` rather than spinning forever: it does not claim the run failed, because it may still be queued, but a stalled queue worker must not present as a slow one. `GET /results/{id}` also takes a numeric stored result id, so any run can be fetched in full later.
- **Every response carries a `state` naming which of several honest answers it is**, rather than leaving a caller to infer one from an empty list — the same distinctions the Livewire components draw, because a React card and a Livewire card describing the same row must not disagree about which piece of news it is. An empty opportunities list is `none` or `not-measured`, and reporting a run that never asked for the performance category as "no opportunities" would tell an operator their page is clean on the strength of a test that never examined it. An empty vitals panel is `no-field-data` or `failed`, and page-level data CrUX filled in from the origin is reported as `origin-level` rather than as a measurement of the page. A blank trend is `empty` or `out-of-range`, which have different remedies. A category the response never carried is left out of the scores array entirely rather than sent as a null, so a client can tell "not measured" from "measured and unscored"; a completed run that lost a plotted measurement is emitted as a null point so a client breaks its line at the hole rather than drawing a confident straight line across a fortnight when testing silently stopped; and failed runs are excluded from a trend rather than plotted as zero.
- Bands are computed server-side against Google's published thresholds; labels and colours are not sent. A band is a fact about where a number falls, and duplicating that arithmetic in every client is how two surfaces of one dashboard come to disagree about whether a page is green — while a label baked into a JSON endpoint hands every caller a string in the server's locale rather than the reader's.
- A form factor, metric, or range the endpoints do not recognise is reduced to the documented default rather than answered with a 422, which is what the Livewire components do with the same values: these are selectors with a fixed set of options, and a payload naming something outside the set is not a request for the nearest one. The URL is the exception — it is the subject of the request rather than one of its options, so an unusable one is answered rather than guessed at.
- `Support\TrendSeries` — the bounds a trend is drawn inside (how far back a range reaches, how many points may be plotted, how few of them stop being a trend) moved out of the Livewire chart, which now reads them from it. They are decisions about the history table rather than about any one surface, and two copies of `MAX_RESULTS` is two answers to "why does my chart stop three months ago".
- `pagespeed:test {url} {--strategy=} {--categories=} {--store} {--json}` with `--min-performance=`, `--min-accessibility=`, `--min-best-practices=`, `--min-seo=`, `--max-lcp-ms=`, `--max-cls=`, and `--max-tbt-ms=` budgets — the CI entry point, and the one command in the package that waits out a 20–60 second run rather than queueing it, because a pipeline has nowhere to put a queued job and nothing to do while it waits.
- **A budget is never satisfied by a score that did not come back.** A budget checked against a null or absent measurement is reported as *unavailable* and exits non-zero, worded apart from a score that fell short, because "accessibility is 40" and "accessibility did not come back" are different problems with different fixes. Treating an absent score as a pass produces a green pipeline that is green precisely because the thing it was installed to catch stopped being measured, which is worse than having no budgets at all. When both happen in one run the unavailable measurement outranks the violated budget: it says the run itself cannot be trusted, and a developer sent to investigate a regression that may not exist is a developer sent to the wrong place. Both are still listed.
- **Four documented exit codes rather than one failure code**, so CI can branch on them and a build log says which bucket it is in: `1` a violated budget, `2` unusable arguments, `3` no API key configured, `4` a failed run, an unavailable budgeted measurement, or a `--store` write that could not be made. That last one is caught rather than allowed to bubble out of the command, because an uncaught exception exits `1` — the code that means a violated budget, and a build failing for a reason it names wrongly is the one outcome a command built around distinct exit codes cannot afford. They are documented in `--help` as well as the README.
- **The API key is checked before the request, not after.** Without the preflight the CI experience is a 20–60 second wait ending in a raw 429, which in a pipeline reads as a flaky API rather than as the one-line configuration fix it is. The check costs nothing and fails in its own class, distinct from a genuine regression.
- A budget on a category `--categories` did not request is refused before the request goes out rather than reported unavailable a minute later — it could never have been checked, so it is a typo rather than a regression. The same applies to a metric budget without the `performance` category, since lab metrics only arrive with it. `--categories=all` repeats the `category` parameter once per category, which is what stops a run reporting three empty scores and passing every non-performance budget silently.
- `--json` emits one document and nothing else, carrying `status`, `failure_class`, `exit_code`, scores, metrics, warnings, the stored row id, and each budget's flag, target, actual value, and `pass`/`fail`/`unavailable` verdict. The failure paths emit the same envelope with an `error` message rather than dropping to plain text, because a CI annotation is only as good as what is in the payload.
- Everything the run tolerated — Lighthouse's own `runWarnings`, absent categories, missing lab metrics, absent CrUX data — is printed as warnings and included in `--json`, so a quiet run and a degraded run never look identical on stdout. A Lighthouse `runtimeError` is reported with its code and message verbatim, in the run-failure class.
- `--store` saves an ad hoc run into result history, with a null `pagespeed_url_id` unless the URL is already monitored, in which case it joins that URL's history. Deliberately nothing else the scheduled path does: no hooks fire and no regression alert is raised, because a CI run's audience is the pipeline that invoked it and a branch build must not page the team.
- `Data\TestResult::warningList()` and `TestResult::describeWarnings()` — the warning lines a thin result is explained with, moved onto the DTO and driven by the warning record's shape, so the CLI (which holds a parsed run) and `PageSpeedResult::warningList()` (which holds the same record in a json column) say the same thing rather than keeping two copies that drift.
- `Alerts\RegressionDetector` — runs after each completed result and compares it with the previous completed run for the same URL and form factor. Two things make a category alertable: an absolute floor from `alerts.thresholds`, and a fall of at least `alerts.drop_points` (10) against the previous run. A category that breaches its floor *and* lost ten points is one piece of news rather than two, and the floor is named first because "below 50" is the more actionable half. Floors are absolute rather than comparative, so they also apply to a URL's very first run — a page that has been bad since the day it was added is not less bad for having no history.
- **A category that stopped being measured is alerted on in its own words.** A score that was there last run and is null now leaves the detector with nothing to subtract, and the obvious implementation says nothing at all — which is the exact failure this feature exists to prevent, arriving through the front door. It is reported as a third kind of regression, worded apart from a numeric drop, because nothing got slower: the page is no longer being measured for it, and somebody has to know that.
- **Degraded runs do not skew the comparison.** A run that completed while losing a category or a lab metric is passed over when looking for a baseline, so a clean run following a thin one is not read as a recovery it never made. The search reaches ten runs back before giving up, so a URL whose every recent run was degraded reports "nothing to compare" rather than resurrecting a year-old baseline nobody would recognise; turn the skip off with `alerts.skip_degraded`. Degradation on the *current* run is never a reason to stay quiet — the notification says the run was degraded instead. Failed runs are never a baseline at all: they carry no scores, so comparing against one would read every recovery as a hundred-point gain.
- **The no-previous-result case logs at debug level** rather than returning silently, so "why did I not get an alert" is answerable from the log rather than by reading the source.
- `Notifications\ScoreRegressionNotification` over standard Laravel channels, with recipients from `alerts.mail_to` (an array, or a comma-separated string as an env var supplies it) and/or a container-resolvable `alerts.notifiable`. Every string is translatable and the counts pluralize. A notifiable that cannot be resolved and a mailer that throws are both logged and swallowed: alerting sits downstream of a queued run that has already stored a perfectly good result, and failing that job would re-test the URL, spend quota, and arrive back at the same broken mailer.
- `Alerts\AlertDispatcher` and `Jobs\SendRegressionDigest` — the digest. One monitoring cycle produces N URLs × 2 form factors of results, each inspected in its own job on its own worker, and alerting on each directly turns one bad deploy into thirty near-identical emails, which is how an alert becomes something people filter into a folder. Regressions are buffered in the cache for `alerts.digest.wait` seconds (300) and sent as a single notification; exactly one flush job is queued per window, claimed through an atomic `add()` so concurrent workers cannot each schedule their own. The buffer is appended under a cache lock where the store provides one, and unguarded rather than blocking a worker where it does not. Recipients, channels, and the digest are deliberately not specific to score regressions — the staleness detector planned in #19 delivers through the same dispatcher rather than growing a second copy of all three.
- `ap.pageSpeed.scoreRegressed` (saved row, regression details) action, fired per result at detection time rather than when the digest goes out, so a listener sees the regression whether or not anybody is configured to be emailed about it.
- `config/pagespeed-insights.php` gains an `alerts` block: `enabled`, `drop_points`, `thresholds` per category, `skip_degraded`, `channels`, `mail_to`, `notifiable`, and `digest`. Thresholds ship unset, because a floor is a per-site judgement and a guessed one either alerts on everything or on nothing.
- `pagespeed:prune {--dry-run}` and `Support\RetentionPolicy` — retention on the results table, in two windows rather than one. Results past `retention.days` (365) are deleted; results past `retention.keep_raw_days` (30) keep their scores and lose their `raw_response`. The split is the whole design: a score row is a few dozen bytes and is the entire reason history exists, while a retained payload is hundreds of kilobytes of data the package has already parsed into its own columns, kept only so a parsing problem can be diagnosed against a real response — a question a month-old payload has either answered or never will. Without any of this an hourly cadence on 200 URLs across both form factors writes about 3.5 million rows a year.
- Both windows measure from `created_at` rather than `fetched_at`, because `fetched_at` is Google's own analysis timestamp and is null on a failed run — and retention has to be able to expire a failed row too. A window applies only when it reads as a positive whole number of days no larger than a century: `0`, a negative, a blank env var, a typo, and a value so large that `subDays()` overflows past it all mean **off**, because the other reading is a cutoff in the future and a cutoff in the future matches the entire table. That last case is not hypothetical — a day count near `PHP_INT_MAX`, which is what `(int)` makes of an env var written in exponential notation, wraps around to *tomorrow*. A window that is off is stated on the command's output rather than passed over silently, so an operator who has just turned one off by accident learns it from the command that was supposed to be doing the work rather than from the disk usage six months later.
- Deletion runs before stripping, and the stale-payload query excludes rows the deletion window has already claimed — which changes nothing about a real run, but stops `--dry-run` promising to strip payloads off ten thousand rows it is about to delete outright. Both windows work in chunks of 1,000 keyed on ids read first, rather than `delete ... limit`, which MySQL takes, SQLite only takes when compiled with an option most builds leave off, and Postgres does not take at all. The first prune of a table that has been growing for a year is exactly the case this command exists for, and it must not be one unbounded statement holding a lock every write path needs.
- `Models\PageSpeedResult` is now `Prunable`, so an application that already runs `model:prune` over its own models sweeps this table along with them. It is not the path the package schedules for itself: `Prunable` hydrates and deletes one model at a time, and knows nothing about expiring a single column.
- The service provider registers `pagespeed:prune` **daily**, under the same `scheduling.enabled` flag as the hourly monitoring task. Daily because a day's worth of results is a rounding error against a year-long window, and registered by the package because retention that has to be wired up by hand is retention most installs never get.
- `config/pagespeed-insights.php` gains a `retention` block — `days` (`PAGESPEED_RETENTION_DAYS`, 365, a full seasonal cycle so this year's Black Friday has last year's to compare against) and `keep_raw_days` (`PAGESPEED_RETENTION_KEEP_RAW_DAYS`, 30).
- `Jobs\RunPageSpeedTest` — the queued run, one URL and one form factor per job. Split that way because a run blocks its worker for 20–60 seconds, and because a mobile run that fails should not take the desktop result down with it. The three ways a run can fail get three different responses, and conflating any two of them is the worst failure mode this package has. A **missing API key is never retried**: keyless PageSpeed answers HTTP 429, the same status as genuine quota exhaustion, because Google's shared anonymous project has a daily quota of zero — so an install that simply never set `PAGESPEED_API_KEY` would otherwise release and retry forever, silently, and present as a broken queue rather than as the one-line configuration fix it is. It fails immediately instead, writes exactly one `failed` row whose `error_message` names both cause and remedy, and logs at error level. A genuine `QuotaExceededException` on a configured key **releases** with a long delay rather than consuming a retry, since the same request will succeed once the window rolls over. Everything else is retried with backoff and recorded as failed once the attempts run out — that last path is covered explicitly, including `failed()`, because a job that dies without ever writing `status = failed` leaves a monitored URL that quietly stops producing history, and a regression detector comparing runs then has nothing to compare and reports nothing wrong. Degraded runs keep their warnings rather than storing a thin row that looks normal, and every log line carries url, strategy, exception class, and attempt number.
- The monitored row travels with the job as an id rather than as a serialized model, so a URL an operator deletes while its job is queued does not make the job explode on unserialization. The run finishes and its result is kept as history for the URL itself, which is what the denormalized `url` column on `pagespeed_results` was for.
- `Jobs\Middleware\RateLimitPageSpeedRequests` — an `Illuminate\Cache\RateLimiter`-backed job middleware holding the whole application to `rate_limit.per_minute` (default 30). The budget is counted under one fixed key rather than per URL, because Google attributes quota to the API key and not to the page being tested; counting per URL would let fifty workers each testing a different page sail past a limit none of them individually broke. Over-budget jobs are released with the limiter's own retry-after, so a large cycle spreads itself out instead of burning retries against a wall. The default is conservative because Google publishes **no** PageSpeed Insights rate limit — not in the Get Started guide, the API reference, or the FAQ — which makes the commonly cited 25,000/day and 100/100s figures folklore rather than documentation. Built directly on the limiter rather than on Laravel's `RateLimited` middleware, which needs a named limiter registered at boot and would therefore freeze the limit at the moment the service provider ran.
- `Scheduling\TestScheduler` — finds the URLs owed a run and queues one job per configured form factor. A cycle **short-circuits entirely** when no API key is configured, with a single log line, rather than fanning out N URLs × 2 strategies of jobs that each fail for the same reason: one loud error beats a hundred quiet ones, and every one of those jobs would cost a queue slot to learn something the scheduler already knew before it started. `dispatchFor()` is the manual counterpart and deliberately ignores due-ness — an operator naming a URL has already decided it should be tested.
- The scheduler persists hook-contributed URLs before a cycle, the one place in the package that calls `UrlRegistry::persistHookUrls()` automatically. It has to: an unsaved model has nowhere to record `last_tested_at`, so a URL registered through `ap.pageSpeed.registerUrls` would read as due on every single cycle whatever its cadence says, and its results would have no parent row to hang history from. Turn it off with `scheduling.persist_hook_urls`.
- `pagespeed:monitor {--url=}` — the manual and scheduled entry point. `--url=` tests one monitored URL now whether or not it is due, matching the address in any spelling, and warns rather than refuses when the URL is paused. The credential preflight is repeated here so an operator gets the answer on their terminal rather than only in a log file.
- The service provider registers `pagespeed:monitor` **hourly**, disabled in one flag with `scheduling.enabled`. Hourly is how often the package *looks*, not how often it tests — a URL only comes due once its own interval has elapsed — and anything less frequent would make `hourly`, a supported per-URL cadence, unreachable. Registered through `callAfterResolving` and reading the flag at resolve time, so an application that never resolves the scheduler does not pay for one.
- `ap.pageSpeed.beforeTest` (url, strategy, monitored row) and `ap.pageSpeed.resultStored` (saved row, parsed result) actions. The second fires for failed rows too, with a null `TestResult`, so a listener can alert on a run that stopped producing data rather than only on ones that succeeded.
- `config/pagespeed-insights.php` gains `queue`, `rate_limit`, `job`, and `scheduling` blocks. `last_tested_at` is stamped only by a run that produced a measurement: it means "when this URL was last measured", and letting a failure satisfy the cadence would make a URL that has quietly stopped being testable read as freshly tested — the exact state the failure row exists to expose. A URL failing permanently is therefore re-dispatched by every cycle until somebody fixes or pauses it.

- `Urls\UrlRegistry` — the single answer to "which URLs are monitored?", merging the stored rows with whatever the `ap.pageSpeed.registerUrls` filter contributes and deduplicating the two by canonical URL. Hook contributions come back as **unsaved** models: a package that registers `/checkout` and is later uninstalled should stop contributing that URL, not leave an orphaned row nobody remembers adding, so persisting one is an explicit `persistHookUrls()` call rather than a side effect of reading the list. Where both sources name the same page the stored row wins, because it is the one with history, an operator-set label, and an `is_active` flag somebody chose. A hook callback that returns a non-array, or contributes a `mailto:` URL, a blank string, or an array with no `url` key, has that entry dropped and logged rather than throwing — one badly written callback in an unrelated package must not take down the whole monitored set. Neither a hook entry nor a CRUD caller can set `source`: how a URL entered monitoring is recorded by the registry, not chosen by the caller.
- CRUD on the registry — `add()`, `update()`, `delete()`, `activate()`, `deactivate()`, `import()`, `find()`, and `findStored()`, for the UrlManager Livewire component and the HTTP endpoints to build on. `add()` is idempotent: adding a URL that is already stored updates the attributes that were supplied and leaves the rest, and its history, alone, which is what makes re-running sitemap discovery safe. `import()` reports `added` / `existing` / `skipped` separately and never touches an existing row, so a re-run cannot silently reactivate a URL an operator deliberately paused. `update()` refuses to move a row onto an address another row already monitors, which would otherwise surface as a `QueryException` out of the unique index — a 500 rather than an answer; callers that need to explain the refusal should pre-check with `findStored()`.
- `Urls\UrlNormalizer` — the canonical form every URL is stored and compared in. Without one, `https://example.com/about`, `https://example.com/about/`, and `HTTPS://Example.com/about#team` become three monitored URLs with three separate score histories for one page. Only differences that cannot change which document is served are erased — scheme and host case, the default port, the fragment, a trailing slash on a non-root path — so query strings survive (`?page=2` is a different page) and `www.` survives, because whether the two hosts serve the same document is a fact about a particular site's DNS, not about URLs. Non-http(s) schemes and URLs longer than the 500-character column are rejected rather than stored truncated into a row that points somewhere else. Embedded `user:pass@` credentials are the one thing dropped rather than preserved: keeping them would write a password in plaintext to the `url` column, the console output of sitemap discovery, and every admin screen listing monitored URLs, and would buy nothing for it, since PageSpeed fetches the page from Google's own infrastructure where userinfo in a URL is not honoured.
- `Urls\SitemapDiscoverer` — walks `sitemap.xml`, following sitemap index files, and returns the page URLs it lists. Parsing is tolerant because sitemaps in the wild are not the sitemaps in the specification: a document libxml can only partly read still yields the entries above the damage, a child sitemap that 404s is logged and skipped rather than throwing away the hundreds of URLs its siblings listed, and `<loc>` is read by local name so a prefixed namespace parses the same as the default one. The tolerance stops at the entry point — the sitemap the caller actually named throws a `SitemapException` instead, because reporting "0 URLs found" when the address 404s is the kind of quiet failure that costs an afternoon. A sitemap is an untrusted document whose whole purpose is to name more documents to fetch, so a run is bounded four ways — discovered URLs, recursion depth, documents fetched, and a requirement that a child sitemap live on the same host as the index that named it — and parses with `LIBXML_NONET` and entity substitution off. The host requirement is what the sitemaps.org protocol already mandates absent a cross-submit verification this package cannot perform, and without it any sitemap the application is pointed at becomes a list of addresses the application will fetch on the author's behalf, reaching loopback services and link-local metadata endpoints that no egress firewall would see. Page URLs on other hosts are still listed, because those are fetched by Google rather than by this application. An index that points at itself terminates, and an external-entity payload is inert. Redirects are followed only for the sitemap the caller named — never for one a document pointed at, since the host check runs on the address before the request and a child answering `302 http://169.254.169.254/` would otherwise walk straight through it. A document is also required to be rooted at `<urlset>` or `<sitemapindex>`: recovery-mode parsing succeeds on an HTML error page, and a custom 404 served with a 200 status is common enough that "0 URLs found" would otherwise be the only symptom of a wrong address.
- `pagespeed:discover-sitemap {--sitemap=} {--limit=} {--activate}` — lists what it found and stores it as `source=sitemap`, **inactive** unless `--activate` is passed. That default is not timidity: a 500-page sitemap activated in one command is 1,000 API requests per cycle against a quota the operator has not looked at yet, and reviewing the list costs far less than discovering a burned quota. The limit defaults to `pagespeed-insights.sitemap.limit` (50 out of the box) rather than being hardcoded in the signature, so raising the cap is a config change instead of a flag on every invocation.
- `config/pagespeed-insights.php` gains a `sitemap` block — `url` (null means `sitemap.xml` at `app.url`), `limit` (50), and `timeout` (15 seconds per sitemap document, since an index file means one run fetches several).
- `Exceptions\SitemapException` — the named sitemap could not be read, distinguishing an invalid address, an unreachable one, a transport failure, and a body that is not XML.

- `Models\PageSpeedUrl` — the monitored-URL model, with `active()`, `due()`, and `forUrl()` scopes and a matching single-row `isDue()`. One row per URL rather than per URL-and-form-factor, so moving a page from mobile-only to both does not fragment its history. `due()` resolves each row's `test_frequency` override against the package default entirely in SQL, so finding the handful of URLs owed a run does not mean hydrating the whole monitored set. A cadence the package does not recognise — a value a later version added, or a typo — is treated as the default rather than skipped, because a URL that silently stops being tested is worse than one tested on the wrong cadence.
- `Models\PageSpeedResult` — the result-history model, with `forUrl()`, `latestFor()`, `completed()`, and `failed()` scopes. `forUrl()` matches the denormalized `url` column rather than the foreign key, so ad hoc runs and runs whose monitored row was later deleted stay part of a URL's history; `latestFor()` breaks a same-second tie on the id so two strategies written by one scheduled run come back in a stable order.
- `PageSpeedResult::fromTestResult()` and `PageSpeedResult::toTestResult()` — the DTO ↔ model mapping, round-trip lossless for everything the schema keeps. Rebuilding restores float typing on lab metric values and per-metric savings: JSON has one number type, so a `45.0` the parser produced comes back out of the column as the integer `45`, and `Opportunity::weight()` sorts on those numbers. The builder that records a failed run is `fromFailure()`, not `failed()` — Eloquent resolves a real static method before it considers a scope, so sharing the name would have silently broken `PageSpeedResult::failed()` as a query at every call site.
- A `warnings` json column on `pagespeed_results`, carrying Lighthouse's own `runWarnings` plus everything the parser tolerated: unrecognized categories, requested-but-absent categories, missing lab metrics, and whether CrUX had data. `PageSpeedResult::hasWarnings()`, `wasDegraded()`, and `warningList()` read it without each consumer re-parsing the JSON. The two accessors are deliberately different questions: absent CrUX data is a warning but not degradation, since it is ordinary for a low-traffic page, while a category or metric that was requested and did not come back is a hole the trend chart will draw straight through. Without this, a run that quietly lost three of four scores is indistinguishable six months later from a page that genuinely only scored on one.
- Storing a result whose response carried a Lighthouse category this package has no column for drops the category, logs a warning naming it, and records it in `warnings` — the write must not fail over a lineup change, but it must leave a trace. The log happens again at write time even though the parser already logged it at parse time, because a queue sits between the two and only the second proves the data is actually gone.
- `pagespeed_urls` and `pagespeed_results` migrations, loaded automatically and publishable under the existing `pagespeed-insights-migrations` tag. The `pagespeed_url_id` foreign key is nulled rather than cascaded on delete, so un-monitoring a URL does not destroy its score history. `pagespeed_results.final_url` is stored alongside `url` so the DTO's redirect target survives the round trip.
- `PageSpeedUrlFactory` and `PageSpeedResultFactory`, with states for the runs that mislead: `failed()` (every measurement null, so a failure is never averaged into a trend as a zero), `withoutFieldData()`, `poor()`, and `degraded()` — a run that completed while quietly losing two categories and a lab metric.
- `config/pagespeed-insights.php` gains `test_frequency` (default `weekly`) and `store_raw_response` (default `false`). Raw payloads are off by default because one response runs to hundreds of kilobytes; retaining every one grows the history table by two orders of magnitude for data the package already parses into columns.
- `illuminate/database` is now a required dependency, and `database/factories/` is PSR-4 autoloaded under `ArtisanPackUI\PageSpeedInsights\Database\Factories\`.
- `Api\PageSpeedClient` — client for `runPagespeed`, with the credential resolution order API key → OAuth bearer token from a connected `artisanpack-ui/google` account → refuse. The third tier throws `MissingApiKeyException` **before** sending, rather than spending 20–60 seconds on a request Google's zero-quota anonymous project is guaranteed to reject. The API key travels on the `X-goog-api-key` header rather than the documented `key=` query parameter (both verified working live), so it never reaches a URL: Guzzle appends the full request URI to its connection-error messages, which puts a URL-borne key straight into exception reports and logs. `PageSpeedApiException` additionally redacts any `key=` or `access_token=` it finds in a transport message, for applications that point `endpoint` at a URL with one embedded.
- `Api\PageSpeedRequest` — validated url / strategy / categories / locale value object. Always sends an explicit `strategy` (the API defaults to desktop) and repeats the `category` parameter once per category (omitting it returns performance only), translating the lower-kebab response spelling to the upper-snake request enum on the way out.
- `Api\PageSpeedResponse` — the raw-to-DTO parser. Tolerates unknown categories, absent requested categories, missing lab metrics, and missing CrUX data; logs a warning naming the exact key it skipped in every case, and carries the same information onto the result so a thin run can be explained rather than guessed at. Lighthouse's own `runWarnings` are parsed rather than dropped, and a 200 carrying `lighthouseResult.runtimeError` becomes a typed failure preserving the original code and message.
- `Data\ScoreSet`, `Data\LabMetrics`, `Data\FieldData`, `Data\Opportunity`, and `Data\TestResult`. `ScoreSet` keeps typed accessors for the four scored categories while retaining any category Lighthouse adds later; `LabMetrics` covers the five metrics behind the performance score and deliberately omits Time to Interactive, removed in Lighthouse 10.
- `Exceptions\PageSpeedApiException`, `Exceptions\QuotaExceededException`, and `Exceptions\MissingApiKeyException` — three types for three causes, each with an `isRetryable()` posture and a message naming the fix rather than the status code. An unkeyed 429 maps to `MissingApiKeyException`, not `QuotaExceededException`: keyless PSI returns the same status as genuine quota exhaustion, and reporting the first as the second is what makes a never-configured install look like a broken queue.
- Opportunity pruning to `opportunities_limit` (default 10), ordered by estimated saving, with the `ap.pageSpeed.opportunities` filter applied before returning. A filter that returns something other than a list of `Opportunity` instances is ignored and logged rather than obeyed. Identifying an opportunity in Lighthouse 13 needs more than a non-empty `metricSavings`: Lighthouse attaches that to diagnostics and informational audits too, so a page scoring 100 would otherwise report a handful of "opportunities" worth zero milliseconds each. The parser skips the `notApplicable` / `informative` / `manual` / `error` display modes, skips passing audits, and requires a positive estimated saving. Verified against the live API — a page scoring 100 yields none, one scoring 95 yields two.
- `Data\FieldData::PERCENTILE` — the CrUX percentile is **75**, resolved against live keyed responses on 2026-08-02. The API discovery document's claim that v5 carries pc90 is stale; locating each reported value within its own `distributions` buckets bounds the percentile rank it must represent, and across 20 real metrics every bound was consistent with p75 while 8 were incompatible with p90. Labelling a p75 as a p90 would have been a silent correctness bug in every UI built on this.
