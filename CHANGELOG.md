# ArtisanPack UI PageSpeedInsights Changelog

## [Unreleased]

### Added

- `Urls\UrlRegistry` — the single answer to "which URLs are monitored?", merging the stored rows with whatever the `ap.pageSpeed.registerUrls` filter contributes and deduplicating the two by canonical URL. Hook contributions come back as **unsaved** models: a package that registers `/checkout` and is later uninstalled should stop contributing that URL, not leave an orphaned row nobody remembers adding, so persisting one is an explicit `persistHookUrls()` call rather than a side effect of reading the list. Where both sources name the same page the stored row wins, because it is the one with history, an operator-set label, and an `is_active` flag somebody chose. A hook callback that returns a non-array, or contributes a `mailto:` URL, a blank string, or an array with no `url` key, has that entry dropped and logged rather than throwing — one badly written callback in an unrelated package must not take down the whole monitored set. Neither a hook entry nor a CRUD caller can set `source`: how a URL entered monitoring is recorded by the registry, not chosen by the caller.
- CRUD on the registry — `add()`, `update()`, `delete()`, `activate()`, `deactivate()`, `import()`, `find()`, and `findStored()`, for the UrlManager Livewire component and the HTTP endpoints to build on. `add()` is idempotent: adding a URL that is already stored updates the attributes that were supplied and leaves the rest, and its history, alone, which is what makes re-running sitemap discovery safe. `import()` reports `added` / `existing` / `skipped` separately and never touches an existing row, so a re-run cannot silently reactivate a URL an operator deliberately paused.
- `Urls\UrlNormalizer` — the canonical form every URL is stored and compared in. Without one, `https://example.com/about`, `https://example.com/about/`, and `HTTPS://Example.com/about#team` become three monitored URLs with three separate score histories for one page. Only differences that cannot change which document is served are erased — scheme and host case, the default port, the fragment, a trailing slash on a non-root path — so query strings survive (`?page=2` is a different page) and `www.` survives, because whether the two hosts serve the same document is a fact about a particular site's DNS, not about URLs. Non-http(s) schemes and URLs longer than the 500-character column are rejected rather than stored truncated into a row that points somewhere else. Embedded `user:pass@` credentials are the one thing dropped rather than preserved: keeping them would write a password in plaintext to the `url` column, the console output of sitemap discovery, and every admin screen listing monitored URLs, and would buy nothing for it, since PageSpeed fetches the page from Google's own infrastructure where userinfo in a URL is not honoured.
- `Urls\SitemapDiscoverer` — walks `sitemap.xml`, following sitemap index files, and returns the page URLs it lists. Parsing is tolerant because sitemaps in the wild are not the sitemaps in the specification: a document libxml can only partly read still yields the entries above the damage, a child sitemap that 404s is logged and skipped rather than throwing away the hundreds of URLs its siblings listed, and `<loc>` is read by local name so a prefixed namespace parses the same as the default one. The tolerance stops at the entry point — the sitemap the caller actually named throws a `SitemapException` instead, because reporting "0 URLs found" when the address 404s is the kind of quiet failure that costs an afternoon. A sitemap is an untrusted document whose whole purpose is to name more documents to fetch, so a run is bounded four ways — discovered URLs, recursion depth, documents fetched, and a requirement that a child sitemap live on the same host as the index that named it — and parses with `LIBXML_NONET` and entity substitution off. The host requirement is what the sitemaps.org protocol already mandates absent a cross-submit verification this package cannot perform, and without it any sitemap the application is pointed at becomes a list of addresses the application will fetch on the author's behalf, reaching loopback services and link-local metadata endpoints that no egress firewall would see. Page URLs on other hosts are still listed, because those are fetched by Google rather than by this application. An index that points at itself terminates, and an external-entity payload is inert.
- `pagespeed:discover-sitemap {--sitemap=} {--limit=} {--activate}` — lists what it found and stores it as `source=sitemap`, **inactive** unless `--activate` is passed. That default is not timidity: a 500-page sitemap activated in one command is 1,000 API requests per cycle against a quota the operator has not looked at yet, and reviewing the list costs far less than discovering a burned quota. The limit defaults to `pagespeed-insights.sitemap.limit` (50 out of the box) rather than being hardcoded in the signature, so raising the cap is a config change instead of a flag on every invocation.
- `config/pagespeed-insights.php` gains a `sitemap` block — `url` (null means `sitemap.xml` at `app.url`), `limit` (50), and `timeout` (15 seconds per sitemap document, since an index file means one run fetches several).
- `Exceptions\SitemapException` — the named sitemap could not be read, distinguishing an invalid address, an unreachable one, a transport failure, and a body that is not XML.

- `Models\PageSpeedUrl` — the monitored-URL model, with `active()`, `due()`, and `forUrl()` scopes and a matching single-row `isDue()`. One row per URL rather than per URL-and-form-factor, so moving a page from mobile-only to both does not fragment its history. `due()` resolves each row's `test_frequency` override against the package default entirely in SQL, so finding the handful of URLs owed a run does not mean hydrating the whole monitored set. A cadence the package does not recognise — a value a later version added, or a typo — is treated as the default rather than skipped, because a URL that silently stops being tested is worse than one tested on the wrong cadence.
- `Models\PageSpeedResult` — the result-history model, with `forUrl()`, `latestFor()`, `completed()`, and `failed()` scopes. `forUrl()` matches the denormalized `url` column rather than the foreign key, so ad hoc runs and runs whose monitored row was later deleted stay part of a URL's history; `latestFor()` breaks a same-second tie on the id so two strategies written by one scheduled run come back in a stable order.
- `PageSpeedResult::fromTestResult()` and `PageSpeedResult::toTestResult()` — the DTO ↔ model mapping, round-trip lossless for everything the schema keeps. Rebuilding restores float typing on lab metric values and per-metric savings: JSON has one number type, so a `45.0` the parser produced comes back out of the column as the integer `45`, and `Opportunity::weight()` sorts on those numbers. The builder that records a failed run is `fromFailure()`, not `failed()` — Eloquent resolves a real static method before it considers a scope, so sharing the name would have silently broken `PageSpeedResult::failed()` as a query at every call site.
- A `warnings` json column on `pagespeed_results`, carrying Lighthouse's own `runWarnings` plus everything the parser tolerated: unrecognized categories, requested-but-absent categories, missing lab metrics, and whether CrUX had data. `PageSpeedResult::hasWarnings()`, `wasDegraded()`, and `warningList()` read it without each consumer re-parsing the JSON. The two accessors are deliberately different questions: absent CrUX data is a warning but not degradation, since it is ordinary for a low-traffic page, while a category or metric that was requested and did not come back is a hole the trend chart will draw straight through. Without this, a run that quietly lost three of four scores is indistinguishable six months later from a page that genuinely only scored on one.
- Storing a result whose response carried a Lighthouse category this package has no column for drops the category, logs a warning naming it, and records it in `warnings` — the write must not fail over a lineup change, but it must leave a trace. The log happens again at write time even though the parser already logged it at parse time, because a queue sits between the two and only the second proves the data is actually gone.
- `pagespeed_urls` and `pagespeed_results` migrations, loaded automatically and publishable under the existing `pagespeed-insights-migrations` tag. The `pagespeed_url_id` foreign key is nulled rather than cascaded on delete, so un-monitoring a URL does not destroy its score history. `pagespeed_results.final_url` is stored alongside `url` so the DTO's redirect target survives the round trip.
- `PageSpeedUrlFactory` and `PageSpeedResultFactory`, with states for the runs that mislead: `failed()` (every measurement null, so a failure is never averaged into a trend as a zero), `withoutFieldData()`, `poor()`, and `degraded()` — a run that completed while quietly losing two categories and a lab metric.
- `config/pagespeed-insights.php` gains `test_frequency` (default `weekly`) and `store_raw_response` (default `false`). Raw payloads are off by default because one response runs to hundreds of kilobytes; retaining every one grows the history table by two orders of magnitude for data the package already parses into columns.
- `illuminate/database` is now a required dependency, and `database/factories/` is PSR-4 autoloaded under `ArtisanPackUI\PageSpeedInsights\Database\Factories\`.
- `Api\PageSpeedClient` — client for `runPagespeed`, with the credential resolution order API key → OAuth bearer token from a connected `artisanpack-ui/google` account → refuse. The third tier throws `MissingApiKeyException` **before** sending, rather than spending 20–60 seconds on a request Google's zero-quota anonymous project is guaranteed to reject. The API key travels on the `X-goog-api-key` header rather than the documented `key=` query parameter (both verified working live), so it never reaches a URL: Guzzle appends the full request URI to its connection-error messages, which puts a URL-borne key straight into exception reports and logs. `PageSpeedApiException` additionally redacts any `key=` or `access_token=` it finds in a transport message, for applications that point `endpoint` at a URL with one embedded.
- `Api\PageSpeedRequest` — validated url / strategy / categories / locale value object. Always sends an explicit `strategy` (the API defaults to desktop) and repeats the `category` parameter once per category (omitting it returns performance only), translating the lower-kebab response spelling to the upper-snake request enum on the way out.
- `Api\PageSpeedResponse` — the raw-to-DTO parser. Tolerates unknown categories, absent requested categories, missing lab metrics, and missing CrUX data; logs a warning naming the exact key it skipped in every case, and carries the same information onto the result so a thin run can be explained rather than guessed at. Lighthouse's own `runWarnings` are parsed rather than dropped, and a 200 carrying `lighthouseResult.runtimeError` becomes a typed failure preserving the original code and message.
- `Data\ScoreSet`, `Data\LabMetrics`, `Data\FieldData`, `Data\Opportunity`, and `Data\TestResult`. `ScoreSet` keeps typed accessors for the four scored categories while retaining any category Lighthouse adds later; `LabMetrics` covers the five metrics behind the performance score and deliberately omits Time to Interactive, removed in Lighthouse 10.
- `Exceptions\PageSpeedApiException`, `Exceptions\QuotaExceededException`, and `Exceptions\MissingApiKeyException` — three types for three causes, each with an `isRetryable()` posture and a message naming the fix rather than the status code. An unkeyed 429 maps to `MissingApiKeyException`, not `QuotaExceededException`: keyless PSI returns the same status as genuine quota exhaustion, and reporting the first as the second is what makes a never-configured install look like a broken queue.
- Opportunity pruning to `opportunities_limit` (default 10), ordered by estimated saving, with the `ap.pageSpeed.opportunities` filter applied before returning. A filter that returns something other than a list of `Opportunity` instances is ignored and logged rather than obeyed. Identifying an opportunity in Lighthouse 13 needs more than a non-empty `metricSavings`: Lighthouse attaches that to diagnostics and informational audits too, so a page scoring 100 would otherwise report a handful of "opportunities" worth zero milliseconds each. The parser skips the `notApplicable` / `informative` / `manual` / `error` display modes, skips passing audits, and requires a positive estimated saving. Verified against the live API — a page scoring 100 yields none, one scoring 95 yields two.
- `Data\FieldData::PERCENTILE` — the CrUX percentile is **75**, resolved against live keyed responses on 2026-08-02. The API discovery document's claim that v5 carries pc90 is stale; locating each reported value within its own `distributions` buckets bounds the percentile rank it must represent, and across 20 real metrics every bound was consistent with p75 while 8 were incompatible with p90. Labelling a p75 as a p90 would have been a silent correctness bug in every UI built on this.
- `Support\CategoryTranslator` for the request/response category spellings, and `Support\GoogleConnectionResolver` for the OAuth fallback.
- `PageSpeedInsights::client()` and `PageSpeedInsights::test()` on the package entry point.
- `config/pagespeed-insights.php` gains `endpoint`, `categories`, `timeout`, and `opportunities_limit`.
- Checked-in PSI fixtures in `tests/fixtures/` — healthy, poor (origin fallback plus more opportunities than the limit), no CrUX field data, a Lighthouse 13 response carrying `AGENTIC_BROWSING` with `seo` absent, a `runtimeError` result, and a quota error body. No test in the package calls the live API.
- `Contracts\ApiKeyRepository` — the storage contract for the PageSpeed Insights API key (`getApiKey()`, `save()`, `isConfigured()`). Because keyless PSI requests carry a daily quota of zero, `isConfigured() === false` is documented as a hard blocker callers should short-circuit on rather than a soft warning.
- `Configuration\ConfigDriver` — reads `PAGESPEED_API_KEY` / `config( 'pagespeed-insights.api_key' )`. Read-only; `save()` throws a `RuntimeException` naming the drivers that can persist a key.
- `Configuration\DatabaseDriver` — stores the key in the new `pagespeed_configurations` table, encrypted with the framework `Encrypter`, with a per-request cache and a `flush()` escape hatch. An undecryptable value logs a warning and degrades to unconfigured instead of throwing.
- `Configuration\CmsSettingsDriver` — stores the key via the CMS framework's Settings module under `artisanpack_pagespeed_api_key`. Encryption lives in the sanitize callback registered by the service provider, so both the driver and the Settings UI write the same ciphertext shape.
- `config/pagespeed-insights.php` with the `api_key` and `driver` keys, published under the `pagespeed-insights-config` tag. The comments state that an API key is required and that there is no supported keyless mode.
- `pagespeed_configurations` migration, loaded automatically and publishable under the `pagespeed-insights-migrations` tag.
- Driver selection via `PAGESPEED_CONFIG_DRIVER` (default `config`), bound in the service provider so the configured driver is re-read on each resolve, plus `PageSpeedInsights::config()` for reaching the active repository.
- Package scaffold generated from `package-blueprint`, following `artisanpack-ui/google-search-console` as the closest sibling reference.
- `composer.json` — `ArtisanPackUI\PageSpeedInsights` PSR-4 namespace, MIT license, `php ^8.2`, `illuminate/support ^10.0|^11.0|^12.0|^13.0`, and required `artisanpack-ui/core`, `artisanpack-ui/hooks`, `artisanpack-ui/google`, and `guzzlehttp/guzzle` dependencies. `suggest` entries for `livewire/livewire`, `artisanpack-ui/cms-framework`, and `artisanpack-ui/livewire-ui-components`.
- `PageSpeedInsightsServiceProvider` with the `pagespeed-insights` singleton binding, auto-discovered by Laravel.
- `PageSpeedInsights` facade and `pageSpeedInsights()` helper, both resolving the same container instance.
- Code style toolchain — `.php-cs-fixer.dist.php` and `phpcs.xml`, with `lint`, `fix`, `cs`, `cs:fix`, and `test` composer scripts.
- Pest + Orchestra Testbench setup with a base `TestCase` and coverage of the boot, binding, facade, and helper paths.
- CI workflow running lint plus the test matrix across PHP 8.2–8.4 and Laravel 12–13, and a release workflow that publishes to Packagist on tag.
- `docs/psi-api-reference.md` — PSI API endpoint, parameter enums, response schema, quota behaviour, and Lighthouse scoring, verified against the live discovery document and a live API probe on 2026-08-01. Records two findings that change the plan: keyless requests now carry a daily quota of **zero**, so an API key is effectively required rather than merely recommended; and the `category` enum has gained `AGENTIC_BROWSING` while `PWA` is deprecated, confirming the parser must tolerate unknown and absent categories.
